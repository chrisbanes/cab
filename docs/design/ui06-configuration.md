# UI06 configuration and recovery contract

The React operator provides the setup, configuration and recovery surfaces, served by the existing listener. Authenticated task, profile, assignment and Runtime HTML controls stay reachable; project configuration uses React Settings. UI07 (#745) owns final visual/usability parity; these surfaces do not qualify release, cutover, real provider access or native structured input.

## Configuration and receipt behavior

Settings is `/app/settings`. Profile and paused-project creation are separate recorded steps. Guided project setup (`/app/settings/projects/new`, ADR-1009) records the name, lead, optional instructions, verified repositories and one optional inactive GitHub Project source in a single `project.create`; repository rows come from GitHub discovery or typed `owner/name` and ref, and each checkout is chosen by typed path or the service folder picker. Creation starts no execution. Project/profile edits omit unchanged optional private input; an explicit empty instruction replacement clears it. Forms edit current values in place: project name, lead and pause; profile name, summary, capabilities and revocation; routing enablement and candidates; GitHub sources and readiness; and, in a separate Repositories section, repository links (add, ref, local path, removal). Each form lists every change under "Changes to save" and enables Save only when that list is not empty. The signed-in operator reveals and edits project and profile instructions, routing guidance and saved search queries in place, and repository paths display plainly. Reveal reads `GET /api/operator/projects/:id/private-values` or `/profiles/:id/private-values`: session-only (every CLI credential, of either scope, gets 403), `no-store`, the exact text with the section version it was read at, never recorded, and absent from the configuration reads, lists and CLI output. An unedited reveal is never sent: `project.configure`, `profile.configure` and `routing.configure` omit `instructions` or `guidance` to keep the saved text, `github.configure` keeps a saved selection with `{id, keep: true}`, and `repositories.configure` keeps a saved repository link by omitting `path`; the service resolves each from its own configuration at the fenced `expectedVersion`. Project filters stay write-only. A changed search query keeps its saved ID (`{id, kind: "search", query}`) and reads inactive until previewed; any other changed source definition is a removal plus a new source with a fresh ID, added inactive. New source IDs are sequential `S-<n>` values when every saved identity is visible; when any is withheld, independent UUIDs prevent collisions without exposing it. Conflict review uses the same allocation rule. Repository links are project configuration with their own version and command (`repositories.configure`, scoped `project:<id>`, each link recording its code host and host name); `github.configure` does not carry them; a recorded `github.configure` that did still replays its receipt. Saving links changes no GitHub source version or selection. Removing every linked repository needs an explicit confirmation. Project current-value edits use React Settings; profile edits also remain at `/profile/:id`. Credential references support omission to preserve, null to clear, or a valid environment reference to set. Credential values are server-only. Operator configuration inputs support omission to preserve their existing references; persisted credential contracts remain unchanged. Normalized delivery and opaque-row saves check the original typed operation receipt before any deliberate same-key retry. Delivery omission and opaque rows are normalized server-side before the unchanged domain command/hash; existing explicit domain commands retain their exact hashes and replay. GitHub domain reference omission remains omitted for its existing canonical hash.

The browser fixes a key, create identity, submitted revisions and validated bytes for each operation. An unknown result freezes that concrete form/resource across same-session internal navigation; explicit reconciliation preserves the original key and payload. Saves requiring delivery or opaque-row normalization first read the original operation receipt; only a not-recorded answer permits a deliberate retry of those frozen bytes. A read failure does not unfreeze the draft. A subsequent rejection/conflict cannot erase prior uncertainty. Matching original receipts stay recorded independently of fresh observations. Later configuration reads cannot replace a receipt or alter a dirty/frozen submission. Editable conflicts require explicit review/adoption of the loaded revision before a new operation. Recorded operations remain separate from latest resource observations.

Each task retains one placement draft. Pending or unknown placement submissions and recorded receipts remain reachable in their initiating presentation project even when the canonical command owner is another membership project and fresh conflict rows disappear. The initiating project is captured separately in authenticated draft memory; it never changes the frozen owner/key/payload or enters command JSON. Placement receipts must match the original chosen project as well as command key, task and version. After an initial definite placement conflict, Review changes in the warning alert explicitly adopts the loaded task version with a fresh key while retaining the chosen membership input. It is unavailable after any unknown outcome, including a later 409 reconciliation response, which preserves the original frozen bytes/key. Mounted fields use React IDs for their own labels and descriptions. Readiness validation retains safe local array indices so the actual first invalid condition receives focus; repository verification retains its fixed safe group error without disclosing diagnostics.

Private draft state lives only in authenticated application memory. Expiry/logout purges it and suppresses delayed completions. Reload or session end discards private drafts: no cross-session browser draft recovery is claimed. There is no configuration localStorage/sessionStorage, private URL field, automatic replay, browser credential resolution or current-state receipt reconstruction. Current/retained instructions, declared credential refs/environment keys/nonempty values and repository/workspace/control paths are excluded from curated JSON, including labels and receipts. Exact private editors retain existing authentication.

Project/profile/routing/source writes retain existing policy and expected versions. Repository verification errors return fixed repositories inline input errors before mutation; diagnostics are discarded. Guided setup also checks each checkout's `origin` against the chosen `github.com` repository and returns `repositories.<n>.path` or `repositories.<n>.ref`; `repositories.configure` and admission keep their origin-free check. The discovery reads (`/api/operator/discovery`, `/repositories`, `/branches?repository=owner/name`, `/projects?repository=owner/name`, `/project-fields?project=<node id>`) are authenticated GETs that do not fail on a credential or GitHub failure: a missing credential or failed read is `unavailable` with a reason code, and nothing is stored. A missing or malformed `repository` or `project` query is 400. `/project-fields` lists a Project's single-select fields and options by name for the readiness Project-field condition picker. When a list is truncated (1000 repositories, 500 branches, 100 Projects, 100 fields), setup says so and accepts a typed repository or ref. The folder listing and checkout check are authenticated POSTs (`/api/operator/setup/folders`, `/api/operator/setup/verify-checkout`) with the session, Origin and CSRF checks, so paths stay out of URLs. `GET /api/operator/setup/home` is a session-only read of the service home folder, or null when it is unusable, for Add Claude's suggested token path; bearer credentials are refused and nothing is recorded. Commit, notification, wakeup and invalid projection failures stay outcome-unknown. Capacity keeps its existing keyed command with no configuration version/CAS; lowering limits holds new admission without terminating active work.

## Source observations and execution recovery

Preview maps the public `github.preview` input to existing `github.activate` authority. A server-only complete command scope/actor/type/key/selection/version/hash lookup replays the original activation before provider access. Fresh preview requires current configuration and a complete version-matched read. Activation does not prove task import or successful sync. The Sync tab names the activated or already-active selection from the confirmed receipt's prior-state field at the loaded source version (a receipt recorded before the field existed says only that the selection is active), marks each selection active or inactive, and offers a refresh that is a separate observation request. The GitHub source tab's Import issues panel chains the two after a save: Preview and import now sends one keyed `github.preview` per saved inactive source, each in an app-wide draft keyed by project, source version and selection so that a lost reply is checked with the same key and never activates a source twice, then one installation-wide refresh. The activation outcome comes only from those receipts; whether anything was imported comes only from the refresh's complete, partial, never or unavailable state, and a failed or unconfirmed refresh claims no import. `/api/operator/source-refresh` is a guarded POST requesting installation-wide observations, with complete/partial/never/unavailable state separate from attempts and available successful timestamps. It creates no domain receipt and accepts no arbitrary provider/project URL. Each complete or partial selection row, the GitHub source tab's Readiness panel and the phone state card show the selection's stored counts ("149 observed (141 closed, not imported) · 9 open · 0 match label `ready`"); a partial read says its counts may be incomplete, and never or unavailable states show none. A complete read with open items and no match warns that imported tasks stay Draft and links to `?tab=github#source-readiness`. A rule withheld by the exclusions reads "rule unavailable" (never "no rule") with no condition text. After a rule change, Ready is re-evaluated only when the selection is previewed and read again, so until then the selection reads "readiness match unknown until the selection is previewed and read again" and its tasks give no unmet reason. The counts come from stored observations only; they are never a readiness grant.

Notifications (`/app/settings#notifications`, between CLI credentials and Readiness) is the only control surface for browser push. Turn on asks the browser for permission and registers the worker only from its own press; Send test notification, Turn off for this browser and Revoke (with a "Revoke <label>?" confirmation) use the session-only routes under `/api/operator/notifications`. The section reads a list that never carries an endpoint or key; this browser is the row whose endpoint digest matches its own subscription, and a subscription that is revoked, removed by the push service or made under another key shows Turn on again. Blocked, unsupported or insecure and service-unavailable states replace Turn on with a plain explanation. Readiness and Home do not list notifications, because they are optional. Phone controls are 44 px. Runtime Settings shows configured/effective caps and actual usage. Recovery at `/app/assignments/:id/recovery` separates captured/configured/current-next revisions from the actual selected admitted generation. Verified task-scoped recovery rows contribute independent Stop, task, writer, capacity and uncertainty holds across the task. The page labels these as task-wide holds, including holds from sibling and omitted generations. It selects the requested assignment's verified rows before applying the newest 20 evidence-row cap in persisted insertion order; the evidence-available state and omitted count describe only that assignment. Foreign or unverified unbound rows are excluded; a selected request without binding can appear only by its exact verified request/assignment identity. Unknown observation kinds remain unknown. Raw process/thread/turn/path/reason data stays out of this projection.

Delivery policy and authority are edited at `/app/projects/:id/settings?tab=delivery`: completion mode, branch prefix, all 17 scoped action kinds, required checks/app bindings and explicit credential Preserve/Set/Clear. Unavailable saved grants, checks and prefix are preserved through version-bound references until explicitly removed or replaced. The former project editor returns 404; the four Settings links and exclusive legacy form handlers are removed. Delivery issue/Project/PR/provider/local facts, guarded Accept handback/Settle as closed and observation refresh are in the task's Changes tab. Settings provides its structured Delivery tab and retains task/Runtime recovery destinations. The authenticated JSON API exposes curated delivery policy with credential presence only, and accepts `delivery.configure` with minimal receipts. Native callback qualification retains its failed one-turn/zero-callback evidence and consumed budget; these surfaces grant no retry or native adapter.

Jira source Settings uses `jira.configure` for site, JQL selections, readiness and closed-issue mode; it is reached through the existing source section or `?tab=github&tracker=jira`. Saved query fields can render empty before their version-matched private read completes; unavailable selections remain opaque keep/remove rows. Validated Jira selections become active when saved under the existing Jira contract; this does not prove an observation refresh or successful import. GitHub configuration saves do not activate selections: GitHub preview/activation and observation refresh remain separate operations.

Excluded source/repository identities are never replaced with sanitized identities. Keep references bind project, section, source kind, version and ordinal; Remove omits the row and Discard restores the loaded draft. Delivery grants/checks use the same version-bound preservation principle. If any projected status-mapping identity cannot be disclosed, the existing optional view is withheld as a whole; stored mapping remains unchanged. Reductions of public status authority still show a conservative warning while that view is absent. Neither withholding nor the warning clears a mapping, changes authority or blocks Save. The legacy project route, four Settings links and eight exclusive form discriminants are absent. Shared project/profile creation, task editing, source review and programmatic form capabilities remain; task editing and source review are in the task workspace, and `/task/:id` is removed.

Advanced original recovery/Apply, task Stop/Resume/dependencies and task edits and Resume source hold are in the task workspace; captured history, messages, results, questions and approvals are in the task view. Recovery is read-only: identities, receipts, acknowledgement and elapsed time do not establish termination or authorize ownership release. Resume clears operator Stop independently of other holds. Phone layouts explain current state and link the desktop-first advanced evidence.

Programmatic dispositions: `assignment.create` remains programmatic as a standalone operation; `/app/tasks/new` supports optional initial assignment atomically with task creation. `assignment.apply`, `dependency.add` and `dependency.remove` retain their exact runtime controls and existing JSON adapters. `imported-blockers.set` has no HTTP/JSON exposure. Project and existing-profile configuration expose an in-place read-only reload. Reload updates observations while retaining dirty replacement inputs, their captured revision/key and any frozen unknown submission. It never confirms a receipt or adopts a revision; deliberate revision review is still required after a definite initial conflict.

## Shared command implementation

Configuration and the task composer share immutable submission ownership, send admission and outcome settlement. Configuration receipt predicates, explicit revision adoption and session-memory privacy remain local. Placement origin, command owner and chosen destination remain distinct. Request-time authentication scope prevents old-session 401 responses from purging newer input while current-session expiry still purges it. See [command lifecycle evidence](../evidence/ui-command-lifecycle.md) for executed proofs and limits.
