This record documents the typed-error conversion and the same-owner repair requested by independent review. The approved scope is [issue #873](https://github.com/chrisbanes/ensemble/issues/873); its accepted implementation plan is [the published plan](https://github.com/chrisbanes/ensemble/issues/873#issuecomment-6133799073). ## Response contract

The API now maps typed domain errors centrally and makes no HTTP decision from `error.message`. Existing public messages and payload shapes are retained. Existing repository-verification errors still carry `fieldPaths: ["repositories"]`; imported title/outcome/readiness refusals do not gain `fieldPaths`.

| Source condition | Response |
| --- | --- |
| Missing task/entity | 404 `not-found` |
| Project mismatch or cross-task authorization refusal | 403 `forbidden`; retained to avoid disclosing another task's existence |
| Existing conflicts, including stale versions, reused keys, changed bindings and retained-evidence identity/material mismatches | 409 `conflict` |
| Invalid input | 400 `invalid-input` |
| Uncertain post-commit outcome or unknown failure | 503 `command-outcome-unknown` / `unavailable` |
| Imported task title, outcome, or readiness mutation | 403 `forbidden` (approved change from readiness 409; no payload additions) |
| Definite operator action limited to `issue.comment` | 403 `forbidden` (approved correction of prior false-positive 409), with the original source message retained |

## Review and verification

Independent review of the first candidate returned `fix-first`: R1 identified the `task.configure` key-lookup priority described above, and R2 identified the 11 omitted prefix literals. Both were repaired in one same-owner batch without changing accepted response statuses or payloads. A later PR review found that removing the generic API target/project precheck also changed priority for `assignment.apply` and dependency add/remove. The same-owner repair adds one shared core preflight for those actual public command types; it preserves 403 ownership refusal ahead of 404 blocker absence, 409 version conflicts, and key collisions, and preserves 404 missing assignment/task and same-project conflict outcomes. The preflight runs before both key gates and again within apply; no API policy duplicate was added. Core-only source review, assignment creation, and imported-blocker commands are explicitly excluded because they are absent from the operator API contract. `test/operator-api.test.ts` covers durable and in-flight collisions plus API response classes and no-write foreign refusals. The remote review reference is [PR #952 discussion](https://github.com/chrisbanes/ensemble/pull/952#discussion_r4253189203); the implementation owner performed no remote writes.

The PR #952 repair followed a fixed-base audit of `src/operator/contracts.ts`: the removed operator command surface contains `task.configure`, `assignment.apply`, `dependency.add`, and `dependency.remove`; `task.configure` already had its own approved preflight. The shared helper was therefore narrowed to `assignment.apply` and dependency add/remove. Core-only `source.review`, `assignment.create`, and `imported-blockers.set` are not part of that API union and keep their existing replay behavior. `assignment.apply` checks assignment identity before project match; dependency commands check dependent-task existence and project match before blocker lookup and version validation. The new preflight is operator-only; existing actor authorization paths remain unchanged. Existing API `requireProject` remains ahead of dispatch. No error message, status mapping, or payload shape changed.

The final removed-boundary audit also preserved `requireTask` visibility semantics. `projectListed` requires a project row joined to its current instruction revision. The new task-target preflight checks target existence, then that the target project is listed, then project ownership. This retains 404 for a task whose own project is not listed before 403 ownership mismatch, key collision, or later blocker/version errors. `assignment.apply` remains on its historical direct assignment lookup path and does not gain a task-visibility check. The regression fixture removes the target project's instruction revision with foreign-key enforcement disabled and verifies `task.configure` and dependency add/remove return 404 against a different listed project for both durable and in-flight keys; this demonstrates an unlisted/incomplete project lookup, not an archive state.

The repair tests cover foreign-project assignment.apply with a stale version (403); missing assignment (404); same-project stale assignment and same-project key conflict (409); foreign-project dependency add/remove with a missing blocker (403, no writes); missing dependent task or blocker (404); same-project stale dependency removal and same-project key conflict (409); and wrong-project/missing-target cases against both durable receipts and in-flight keys. Focused `operator-api.test.ts` selection passed 4/4 tests, including the task.configure visibility regression and dependency cases. A new exact old-project replay-after-placement test is not feasible for these command shapes: GitHub placement accepts only imported tasks and rejects an assigned imported task; dependency creation refuses an imported dependent, while placement rejects an imported task that has a local dependency. The existing `task.configure` transfer/replay regression covers the supported target-transfer boundary.
