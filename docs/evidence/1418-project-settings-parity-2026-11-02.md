### Policy and source dimensions

Both completion modes are available. The 17 action kinds are `issue.comment`, `issue.labels`, `issue.edit`, `issue.create`, `project.item.add`, `project.field`, `issue.status`, `pr.create`, `pr.edit`, `pr.ready`, `pr.merge`, `issue.close`, `pr.thread.reply`, `pr.thread.resolve`, `branch.push`, `branch.force-push` and `branch.adopt`. Branch adoption remains approval-only. Each visible grant retains exact repository/tracker-container ID, allow/approval and accepted supplemental Project ID, field ID and ordered option list. `issue.status` retains its Jira status list; statuses remain invalid on other actions. Project/field/options accepted on other actions are not silently stripped. Absent optional lists differ from explicit empty lists; order and duplicates are retained. Required checks retain name and absent/present app binding, including duplicate check rows.

An absent branch prefix uses the existing delivery default; explicit empty stays empty. A withheld prefix is null plus its unavailable flag and is preserved by the adapter, never fabricated as empty text. Opaque grant/check rows expose only their unavailable label and version-bound saved-row reference. Remove omits the row; Discard restores the current loaded row. UI keys are deterministic for seed rows and explicit for added rows, remain stable through add/remove and never enter policy JSON. Local keyed errors map to numeric API paths; focus waits for the commit showing the first invalid control.

Credentials remain service-only. Reads, receipts and change-list text reveal neither saved reference names nor values. Preserve is the default even when none is configured and sends no reference. Set submits only the newly entered supported environment reference; Clear is explicit null. No credential-kind, default-policy, authority or CLI-write change is part of this work.

Issue/Project/status actions apply to the **issue-tracker container**, independently of code repository links; PR/branch actions apply to the code repository/link. The UI labels that distinction. GitHub mapping coverage uses exact repository/Project/field/option scope; Jira uses exact container/status scope. Covering allow grants form a union, so removal of a duplicate covering grant does not invent a loss. Changing allow to approval or narrowing the last covering scope can warn without changing mapping or blocking Save.

Jira is a separate existing source kind introduced by the integrated #1394 work. The legacy project renderer contains **no Jira form or Jira discriminant**. Jira Settings is selected by the saved tracker or `?tab=github&tracker=jira` within the existing source tab (whose navigation label is still “GitHub source”). It edits site, JQL definitions, readiness and closed-issue behavior; Jira reference management remains its existing authenticated control. Preview matches is an authenticated read. Under the existing domain contract, validated Jira selections are active when saved; a save still does not prove refresh/import. GitHub’s separate preview/activation behavior must not be asserted for Jira.

Public Jira query controls may render before their version-matched private saved-query read completes. While that response is held/unavailable, opaque saved selections remain preserved. Releasing the real response hydrates the expected normalized query. That temporary empty field is not evidence of a lost saved query or permission to submit a replacement for a hidden selection. The repaired journey explicitly verifies both states.
